## 2. Working thesis — a hypothesis to test, not a conclusion

**Asymmetry of oracles.** SE delegation works largely because SE is full of cheap,
executable checks that **fail loudly**: compiler, type checker, linter, test suite, CI.
An agent gets dense feedback and corrects itself. OE has far fewer such checks, and the
ones it has often **fail silently**:

- JSON-LD drops an undeclared key on expansion **without any error** (to verify in the
  JSON-LD 1.1 spec: expansion drops terms that do not expand to an IRI);
- a SHACL shape whose target matches zero nodes reports **CONFORMS**;
- a reasoner on an OWL Full ontology is incomplete or silently repaired by the API;
- "is this the right concept / the right property?" has no executable oracle at all: it
  is a human, semantic judgement.

Consequence to examine: delegating OE to an AI **without building the oracles first**
produces *silent, confident debt* that a beginner cannot see. The remedy is not "less
AI" but **instruments first** (gauges, exact-value gates, negative tests, authority
discipline), then delegation of the mechanical part, with the human keeping semantics.

Test this thesis against the literature (§4–5) and against the case (§3). Look for
counter-evidence too (OE tools that do fail loudly; SE areas with weak oracles).

**Silent debt produced by AI-assisted generation (the ontologies were generated by the
AI on Michel's request; he was not aware of these defects):**

| Defect | Size | How it stayed invisible |
|---|---|---|
| bare JSON keys (declared in no `@context`) | 4177 → 3418 in the canonical corpus after two days of repair; **6604** more in the 43 M0 instances | dropped silently on JSON-LD expansion; files still open and simulations still run |
| `@vocab: owl#` turning bare keys into fake `owl:<key>` terms | 142 terms, 2 files | valid RDF, wrong namespace, no error |
| `owl:imports` written as strings | 173 imports | literals: no reasoner followed any import; every file reasoned in isolation |
| root `@id` + `@graph` (JSON-LD named graph) | 3 files | content absent from the default graph; one file "SHACL-conformant only because invisible" (+24 violations once repaired) |
| a SHACL-generating skill and its script | proposed constraints on properties with 0 occurrences, a dead file name, a phantom namespace | generated shapes would have matched 0 nodes and reported CONFORMS |
| gate texts with stale numbers; a note claiming a SHACL file that is not in the repo | 4 notes | confident text next to correct numbers |

**Earlier silent failures** documented in the gate's own docstring
(`ontology/cli-tools/run_all_layers.py`): a shape enforced on one file only; 256
violations of pure noise; a fixer "called, never defined"; a schema file not found
(dot vs underscore) → validated nothing, exit 0; a whole instance category skipped; a
validator that works in a terminal and dies through a pipe (Windows code page).
"None of them crashed. None of them reported failure."

**Errors made by the AI during the repair itself, caught by instruments:**
- a changelog-trimming edit deleted a whole ontology node in two files → caught by a
  node-count comparison HEAD vs working copy before delivery;
- an earlier lot had introduced `rdf:value`, a reserved OWL term that cannot be declared
  in OWL 2 DL → caught when the corpus was checked against the OWL 2 specification;
- a HandOver (AI-written) stated that OWL 2 allows declaring built-in terms; reading the
  specification showed it is true only for 9 annotation properties.

**What worked (candidate "instruments")**:
- *head-over-memory*: facts come from the repository HEAD, never from the model's memory;
- an acceptance gate with **exact reference values** (a count that drops is as
  suspicious as one that rises; frozen only with a written reason);
- per-lot structural checks: parsed-graph diff HEAD vs working copy, node counts;
- **negative tests** for every new check ("a check that cannot fail proves nothing");
- gauges turning a debt into a number (bare keys, undeclared terms, imports as strings);
- one decision at a time, explained in plain words, taken by the human; the AI executes;
- delivery as patches applied by the human (`git am`), gate run on his machine.

**What the AI did well** (counter-weight): mechanical, verified renames at scale (~760
keys in a day); reading the primary specifications (OWL 2, SKOS, DCMI, ADMS, schema.org)
and choosing by meaning, not by name; finding its own earlier mistakes once instruments
existed.

## 6. The harness / multi-agent question — for Michel's situation

Frame it as questions, answer with evidence:
- What does a *harness* add in OE if the oracles are missing? (Hypothesis: the harness
  that mattered here *was* the oracles — gauges, gate, skills, HandOver loaders — not
  more agents.)
- When does a multi-agent setup help? (Hypothesis: an independent reviewer agent helps
  only if it checks against executable or explicit criteria; otherwise several agents
  multiply unverified output.)
- Budget reality: what the Claude Pro plan includes, its usage limits, and what a
  multi-agent or API-based setup would cost — **check on support.claude.com /
  docs.claude.com at writing time**, never from memory.
- A beginner's minimal viable setup: one assistant + versioned repository + a gate with
  exact values + skills that load the discipline + HandOvers between sessions.
